# Sarab RMS — Project Context

## What this is
Laravel RMS built on top of the static ThemeWagon "Sarab" HTML template. Public site UI (`sarab/` reference copy) must render pixel-identical while becoming DB-driven. Panels: Admin, Customer (account + ordering), Kitchen/Staff, Delivery/Rider. COD only, no payment gateway. Full 18-phase plan lives in the plan-mode history; current progress tracked by phase number below.

## Standing priorities
- Never edit `sarab/` or `Documentation/` — read-only visual/reference baseline.
- New panel UI (admin/kitchen/delivery/account) reuses existing CSS tokens (`.btn-red`, `.stitle`, card patterns) — no bolted-on third-party admin theme.
- Auth is Breeze (Blade stack) restyled to Bootstrap-5 + Sarab classes, not Tailwind.
- Roles via `spatie/laravel-permission`: `admin`, `kitchen`, `rider`, `customer`.

### Visual QA pass — real bugs found via actual browser rendering, not curl
Every verification through Phase 16 was curl/HTTP-status-based, which is blind to layout bugs. Used the Python `playwright` package (already installed on this machine at `~/.local/lib/python3.14/site-packages/playwright`, chromium browser present) driven via a throwaway script to screenshot every panel at 1440×900 and 390×844 (iPhone-sized) viewports, logged in as each role. This caught three real, previously-undetected bugs:

1. **`.fcard` position/display leak (the big one)** — the original template's stylesheet defines `.fcard` *twice*: once (for a small floating decorative badge, `.fcard.fc1/.fc2/.fc3`) with `position: absolute; display: flex; align-items: center; gap: 9px`, and again later (for the generic "white rounded card" look) with only `background/border-radius/padding/box-shadow` — critically, the second rule never resets `position` or `display`, so those first-rule properties silently apply to *every* plain `.fcard` anywhere in the cascade. Phases 6–10 reused bare `.fcard` as a generic card wrapper across `cart/index`, `checkout/show`, `checkout/confirmation`, `account/*`, `partials/account/nav`, and Breeze's `layouts/guest` (login/register) — meaning all of those had `position: absolute` (causing siblings to collapse/overlap each other) and `display: flex` in a single row (causing multi-child cards like the login page's `<h4><p><form>` to lay out side-by-side instead of stacked). Confirmed via screenshot: login page had "Welcome Back" squeezed into a narrow column to the left of the entire form; account dashboard had its nav-pills row overlapping the Recent Orders/Upcoming Reservations cards underneath it.
   **Fix**: added `.simplepage .fcard { position: static; display: block; }` to `layouts/site.blade.php` and `.authbox .fcard { position: static; display: block; }` to `layouts/guest.blade.php` — both scoped strictly to ancestor classes that only wrap the *new* pages, so the original homepage's own `.fcard` usage (the 3 floating `.fc1/.fc2/.fc3` badges, and 2 solitary single-child forms that happened not to visibly break) is completely untouched, preserving pixel-identical fidelity to `sarab/index.html` per the hard project constraint.
2. **Admin/staff panels had zero responsive design** — `layouts/admin.blade.php`'s sidebar was a fixed 250px flex child with no mobile breakpoint at all, eating well over half of a 390px viewport permanently; index-page header rows (`d-flex justify-content-between` with an h5 + a `.btn-red`) would wrap so badly that the pill button's `border-radius: 50px` turned it into a giant circular blob overlapping the heading text. **Fix**: added an off-canvas sidebar pattern (`position: fixed; transform: translateX(-100%)` + `.open` class, hamburger toggle button + JS, dark backdrop) behind a `@media (max-width: 900px)` block, plus rules that stack header rows vertically and make `.table` horizontally scrollable on mobile. Same treatment (topbar wrap + table scroll) added to `layouts/staff.blade.php` for kitchen/delivery, though that layout didn't have the sidebar problem.
3. **`.simplepage` had redundant top padding** — `padding: 160px 0 100px` was added in Phase 7 apparently assuming the topbar+nav were `position: fixed` and needed clearance compensation; they're actually `position: sticky`/static and already push content down on their own (confirmed via `getBoundingClientRect()` — `.simplepage` started exactly where the header ended, zero overlap). The padding was pure unnecessary dead space, worst on mobile. **Fix**: reduced to `60px 0 80px` desktop / `30px 0 50px` mobile — still enough for visual breathing room, no more empty gap.
4. **Cart item row overflow on mobile** — the item row (`[data-cart-item]`) is a single non-wrapping flex row (image + title + qty input + delete + price), which doesn't fit a 390px viewport and clipped the price off the right edge. Fixed with a `@media (max-width: 576px)` rule making that row wrap and the price go full-width on its own line.

**Takeaway**: curl/HTTP-status verification (used through Phase 16) proves routes/forms/data persistence work but is blind to CSS layout bugs. Any future "is this panel working" check should include at least one real-browser screenshot pass (Playwright is available on this machine outside any project's `node_modules` — `python3 -c "from playwright.sync_api import sync_playwright..."` — no MCP server or project-level install needed), not just curl.

### Post-Phase-17 follow-up: homepage mobile "broken layout" report (2026-09-17)
User flagged the live homepage on mobile as showing large empty gaps and missing hero text. Two separate causes investigated:

1. **Real bug, fixed**: `SiteSettingController@update` was clearing `site_settings` rows during earlier manual testing, so `hero_title`/`hero_description`/etc. were empty strings — the hero section rendered its layout correctly but with blank text. Re-seeded via `php artisan app:demo-data`; confirmed fixed via screenshot (hero text renders).
2. **Not a real bug — screenshot-tooling artifact**: after the data fix, full-page mobile screenshots (Playwright `full_page=True`-style capture) still showed huge blank bands below the hero for every remaining section (category, menu, special, gallery, etc.). Root cause: the site uses stock AOS (animate-on-scroll) — `AOS.init({duration:680, once:true, offset:55})` in `public/js/main.js:1`, unmodified stock `aos.css`/`aos.js`, **identical setup already present in the original static `sarab/index.html` template** (not something this build introduced). AOS elements start at `opacity:0` and only flip to `opacity:1` once an IntersectionObserver/scroll callback fires and adds `.aos-animate`. A full-page screenshot taken by resizing the viewport to the full document height in one jump (rather than real incremental scrolling) captures the frame *before* those async callbacks fire, so fully-laid-out, correctly-sized content paints as invisible — box height reserved, nothing drawn. Verified: (a) per-section computed heights exactly match real content height with zero unexplained gap, total equals `document.body.scrollHeight`; (b) a genuinely interactive incremental scroll test (400px steps, settle time) revealed all 45 `.aos-init` elements with 0 stuck; (c) even a screenshot taken *after* a real scroll-through still showed the same blank bands once a `full_page` resize-capture was used for the final image, confirming the resize-capture step itself is what desyncs from the async reveal, not the scrolling. Real mobile users scrolling normally never hit this — there's no scenario where a real device's viewport jumps to full-page height in a single frame.

**Takeaway**: don't trust `full_page=True`-style single-shot screenshots on AOS-animated (or any IntersectionObserver-driven reveal) pages — they will show false "blank gap" regressions. Verify with either (a) a real incremental-scroll interactive test checking `.aos-animate` class coverage, or (b) per-viewport-height screenshots taken while genuinely scrolled to each position, not a resize-to-full-height capture.

## Shipped: Kitchen panel (Phase 14)
- New `layouts/staff.blade.php` — lighter-weight shell than `layouts/admin.blade.php` (no sidebar), shared by Kitchen and Delivery panels since both are single-page operational queues, not multi-section CRUD. ### Gotcha: `@php(...)` inline form can fail to compile with no visible cause
Used `@php($staffPanelName = 'Kitchen')` (the parenthesized inline form) in `kitchen/dashboard.blade.php` and got a 500 — `syntax error, unexpected token "@"` — because it compiled to `<?php($staffPanelName = 'Kitchen')` with **no semicolon and no closing `?>` tag**, which swallowed every line after it (including the literal `@section(...)`) into the same broken PHP block. The identical inline form works fine elsewhere in this codebase (e.g. `admin/categories/_form.blade.php`'s `@php($category = $category ?? null)`), so this isn't a blanket incompatibility — cause wasn't fully isolated. Fix: use the block form `@php $var = 'value'; @endphp` instead, which compiled and rendered correctly, and run `php artisan view:clear` if a 500 persists after fixing the source (stale compiled view). Prefer the block form for any future top-level Blade `@php` variable assignment to sidestep this.

### Gotcha: Blade partial shared between create/edit — undefined variable
A `_form.blade.php` partial `@include`d from both `create.blade.php` (model variable doesn't exist) and `edit.blade.php` (it does) will throw "Undefined variable" if a field does `$model->prop ?? ''` directly — PHP evaluates the property access before `??` can catch it, and `??` only guards undefined *variables*, not property access on an undefined one. Hit this building the Category form, fixed project-wide by prepending `@php($model = $model ?? null)` (the `??` operator IS safe on undefined variables) at the top of every `_form.blade.php`, then using the null-safe operator throughout (`$model?->prop ?? ''`). `@isset($model)` (not `$model !== null`) is used for the `@method('PUT')` line and image-preview blocks since `@isset` is also safe on undefined variables.

### Note: parallel fork build
5 of the 9 resources (Chef, Gallery Items, Testimonials, Blog Posts, Special Offers) were built by parallel fork agents given the verified Category controller+views as an exact template — each fork only touched its own controller/view files, never `routes/web.php` (batched into one route registration afterward to avoid concurrent-edit conflicts on a shared file). All 9 resources were then verified together in one E2E pass by the coordinating session. This pattern (prove one instance manually, fork the mechanical repeats, integrate + verify centrally) is worth reusing for Phase 13 if its operations screens turn out similarly repetitive.

## Shipped: Cart & Checkout (Phase 9)
- Guest cart identified by a dedicated `cart_token` cookie (`CartController::GUEST_COOKIE`), set via `Cookie::queue()` in `CartController::guestToken()` — 1yr expiry, encrypted (standard Laravel `EncryptCookies` middleware handles decrypt/encrypt transparently on read/write within the same app).
- On login, `AppServiceProvider::boot()` registers an `Illuminate\Auth\Events\Login` listener that reads the same `cart_token` cookie, finds the guest `Cart` by `session_id`, merges its items into (or creates) the user's `Cart`, then deletes the guest cart.
- Checkout (`CheckoutController`) requires an authenticated user (`resolveCart()` only builds a session-scoped cart for guests; order creation reads `$request->user()->id` directly), COD-only, generates `SR-XXXXXX` order numbers, empties the cart items on success.

### Gotcha: guest cart merge — don't use `session()->getId()`
Original implementation identified the guest cart by Laravel's session ID (`session()->getId()`). This broke silently: the session ID is regenerated during login (session-fixation protection), so the ID captured before login no longer matches the guest cart's `session_id` by the time the `Login` event listener runs — merge found nothing, guest cart orphaned, user saw an empty cart post-login.
**Fix:** identify the guest cart via an explicit, stable `cart_token` cookie instead of the session ID, read from the *same* cookie name in both `CartController` and the `Login` listener. Verified via full curl-driven E2E (guest add → login → cart merge → checkout → order visible in `/account/orders`) with a clean DB state — confirmed working 2026-09-17.

## Environment gotchas (this machine/session)
- A "dev-agent boundary guard" hook blocks Bash/Write calls referencing any path outside the project root — including paths inside string literals (e.g. `/tmp/foo.log` in a redirect). Route scratch output through an in-project path (`storage/app/scratch/` or similar, cleaned up after) instead of `/tmp` or `$HOME`.
- A PostToolUse PHP formatter hook strips `use` imports that have zero usages *at the moment that specific Edit lands* — including when the class is used elsewhere in the file but the edit sequence is split across multiple back-to-back `Edit` calls. Always add an import in the same `Edit` as a real usage, and re-grep the file for the `use` line after a multi-edit sequence to confirm it survived.
